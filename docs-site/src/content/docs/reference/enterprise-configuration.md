**Available in:** Enterprise

Every Enterprise service reads its configuration from environment variables at startup. A malformed or out-of-range value stops the service and names the variable. Nothing falls back silently to a default.

With the Helm chart, set a variable in the service's `env` map (`api.env`, `backend.env`, `worker.env`, `workerGpu.env`, `rag.env`, `webhooks.env`) or, for a secret, in `extraEnv` or `extraEnvFrom`. The chart's `values.yaml` lists the operator-relevant variables as commented entries in each map. See [Install Enterprise with Helm](/start/enterprise-helm/) for the install procedure.

Related settings live on their own pages: storage in [Storage](/operate/storage/) and [AWS storage](/operate/aws-storage/), RAG in [RAG configuration](/operate/rag-config/), and identity in [Authentication](/concepts/authentication/). Xberg Pro has its own [configuration reference](/reference/pro-configuration/). Variables that both tiers read (database, storage, OIDC, tracing) behave the same way there.

The SFTP source connector's budgets (`SFTP_CONNECT_TIMEOUT_SECS`, `SFTP_OPERATION_TIMEOUT_SECS`, `SFTP_INVENTORY_TIMEOUT_SECS`, `SFTP_FETCH_TIMEOUT_SECS`) apply to the backend and the worker. See the [Pro reference](/reference/pro-configuration/#timeouts-and-shutdown) for their ranges. `SFTP_HOST_ALLOWLIST` lists the exact `host:port` pairs the connector may reach.

The chart names these shared settings as values rather than `extraEnv`:

- `global.observability.otlpEndpoint`, `tracesEndpoint`, `logsEndpoint` and `metricsEndpoint` set `OTEL_EXPORTER_OTLP_ENDPOINT` and the three per-signal `OTEL_EXPORTER_OTLP_{TRACES,LOGS,METRICS}_ENDPOINT` variables on every service. A per-signal endpoint overrides the shared one for that signal. Set alone, it turns on that signal only. A component's `env` map can override one for that pod or, with an empty value, remove it. Any of them opens the collector egress rule in the NetworkPolicies. `OTEL_METRIC_EXPORT_INTERVAL` is a plain `env` entry. See [Observability](/observability/).
- `structuredLlm.thresholds.*` sets the `XBERG_STRUCTURED_*` thresholds and tunables on the workers (`scanMaxCoverage`, `digitalMinCoverage`, `docxTextMinDensity`, `enableFallback`, `fallbackThreshold`, `maxOutputTokens`, `maxInputTokens`, `maxParallelCalls`, `maxExcerptChars`, `maxPageEdge`). An empty value leaves the engine default. Names, defaults and ranges are in the [Pro reference](/reference/pro-configuration/#extraction-models-and-limits).
- `<component>.livenessProbe` and `<component>.readinessProbe` (api, backend, rag, webhooks, worker, workerGpu, frontend) override `initialDelaySeconds`, `periodSeconds`, `timeoutSeconds`, `successThreshold` and `failureThreshold` key by key. The path and port stay fixed. `api.startupProbe` and `rag.startupProbe` are values as well.
- `api.terminationGracePeriodSeconds`, `worker.terminationGracePeriodSeconds` and `workerGpu.terminationGracePeriodSeconds` set the pod grace period and the matching `*_TERMINATION_GRACE_SECS` variable together.

### Long extractions

A large scanned PDF can need more than the default ten minutes, and fails with `Extraction timed out after 600000ms`. Raise the limits below together, because each one caps the next.

1. **Per request.** `extraction_timeout_secs` in the request's `config` (JSON body or multipart `config` part), or in a file's `config-<filename>` part. In seconds.
2. **Ceiling.** `XBERG_EXTRACTION_TIMEOUT_CEILING_SECS` is the most a request may ask for. More is clamped.
3. **Default.** `XBERG_EXTRACTION_TIMEOUT_DEFAULT_SECS` is what a request without the field gets. Raising only the ceiling leaves those requests at 600 s.
4. **Job deadline.** `JOB_TIMEOUT_SECS` bounds the whole job, so the ceiling (and with it the default) cannot exceed it.

For 30 minutes on every document, set these on the worker and, if you run one, the GPU worker:

```yaml
worker:
  env:
    JOB_TIMEOUT_SECS: "1800"
    XBERG_EXTRACTION_TIMEOUT_CEILING_SECS: "1800"
    XBERG_EXTRACTION_TIMEOUT_DEFAULT_SECS: "1800"
```

Also check these:

| Setting                                | Default | Relationship                                                                                                                                                                                                               |
| -------------------------------------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `STUCK_JOB_THRESHOLD_SECS`             | 7200    | Keep it above `JOB_TIMEOUT_SECS`. The reaper fails a processing job older than this, and the worker does not compare the two                                                                                               |
| `ENTERPRISE_PROCESSING_TIMEOUT_SECS`   | 900     | Protected (replicated-mode) submissions only. Set it on the API. It is the fixed deadline of one attempt, and the extraction timeout is cut to what remains of it. Raise it above the ceiling, or those jobs stop at 900 s |
| `XBERG_OCR_CALL_TIMEOUT_SECS`          | 1260    | One VLM OCR provider call, not the document. A page that needs longer fails whatever the extraction timeout is                                                                                                             |
| `XBERG_LLM_CALL_TIMEOUT_SECS`          | 300     | The same for one vision or structured-extraction provider call                                                                                                                                                             |
| `worker.terminationGracePeriodSeconds` | 120     | A worker stopped mid-job has this long to finish. A longer job is redelivered by JetStream and starts again, so a rollout during a 30-minute job repeats it. Raise it to ride out rollouts                                 |

The JetStream ack window (30 s, renewed while the job runs) and its redelivery schedule are provisioned with the stream and do not limit job length.

| `WEBHOOK_BATCH_TIMEOUT_SECS`         | int  | 5       | Fetch window per batch                                                                                                                                                               |
| `WEBHOOK_HTTP_TIMEOUT_SECS`          | int  | 30      | Per-request delivery timeout. In replicated mode it must stay below the 60 s delivery deadline                                                                                       |
| `WEBHOOK_DELIVERY_CONCURRENCY`       | int  | 8       | Concurrent deliveries for one job's webhooks                                                                                                                                         |
| `WEBHOOK_LEDGER_RETENTION_DAYS`      | int  | 7       | How long a delivery-ledger row is kept. Must be 3 to 365. The webhooks stream replays messages for two days, so a shorter retention could purge a row the broker can still redeliver |
| `WEBHOOK_LEDGER_PURGE_INTERVAL_SECS` | int  | 21600   | Gap between ledger purge sweeps. Must be 60 to 86400                                                                                                                                 |

The retry schedule (five attempts, waiting 5 s, 30 s and 5 min) is provisioned into the JetStream consumer and the redelivery relay, so it is fixed at build time rather than read from the environment.
